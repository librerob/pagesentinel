# Architecture

## v0.2.0 preview additions

IndexedDB v3 adds company records without rewriting v2 monitor/text/history stores. Company controls and document metadata updates are atomic and account for company record sizes. Existing v1 migrations remain transactional. Monitors reference a company optionally; separate individual/company pause state preserves per-document choices. Group schedules update inherited intervals only. Removing a company detaches documents without deleting versions.

The existing static network pipeline is unchanged. User-initiated current-tab discovery reads bounded observed links through an isolated script; dashboard discovery uses an approved bounded homepage fetch. Candidates are validated public URLs and require explicit origin grants when selected. Discovery never crawls candidate URLs. Optional document type/language/region labels do not change request headers or silently compare regional variants.

`privacy.ts` contains deterministic discovery/company validation. Policy landmark extraction, paragraph multiset evidence and keyword categories remain local. `items.ts` extracts a selected stable-link list and compares URL identities, independent of ordering. Availability uses an exact complete stock message; generic keywords retain substring semantics. No arbitrary regular-expression evaluation or XPath engine is introduced.

The timeline reads lightweight snapshot metadata and fetches at most 20 selected full versions per page. Read-through timestamps acknowledge document alerts. Snapshot IDs are used for native change-notification IDs; commits precede notification attempts. Bulk updates/deletions use one transaction. Guided repair uses trusted session context and final-tab URL matching, followed by an explicit form save.

`encryption.ts` uses native Web Crypto solely for passphrase backup files. Encryption/decryption runs in the trusted extension UI, never a website script; passphrases are not sent in worker messages or stored. Imported configurations/companies receive fresh IDs and start paused in one transaction, while archival history remains in the file. Normal local storage is not encrypted.

Overview and persisted skippable onboarding introduce the primary workflows. Contextual advanced disclosures preserve existing monitor controls. The permission list is unchanged. Automated axe scans are development-only. See [v3 migration](MIGRATION_V3.md), [backup controls](BACKUPS_AND_MONITORING.md), [security review](SECURITY_REVIEW.md) and [rendered-mode investigation](DYNAMIC_MONITORING.md).

Text/policy alert thresholds use a separate reference text from the latest alert, or the initial successful baseline. Each successful version still advances the ordinary baseline and stores a previous-to-current snapshot. Sub-threshold edits leave the reference untouched; alerts and explicit baseline resets replace it. Failed checks retain both texts. Legacy monitors without a reference begin from their last successful baseline unless retained history supplies a newer alert reference during migration. The percentage remains the existing added-plus-removed character volume divided by the longer comparison text.

`src/core/` contains validated models, inert extraction, bounded network reads, comparison/rule logic, IndexedDB transactions, backup validation and the check state machine. `src/worker.ts` registers Chrome event listeners synchronously and serializes operations. `src/picker.ts` is an isolated-world temporary content script. React interfaces live in `src/ui/`.

The scheduler uses one repeating one-minute alarm. It reconciles permissions, interrupted leases, and missing alarms on installation, browser startup and worker initialization. Browser startup spreads substantially overdue monitors by 15 seconds. Each tick handles the three oldest due monitors sequentially. Saved per-monitor next-check times use a 0–15-second jitter. Failure backoff grows exponentially to six hours while respecting longer configured intervals. Manual-only monitors do not schedule retries.

Before a check, the worker persists last-attempt time and a 45-second lease. Fetch timeout is 18 seconds. Each response is limited to 2 MiB and must be HTML; redirects, credentials, and referrers are rejected/omitted. HTML parsing uses no DOM APIs, offscreen page, tab rendering, script execution or resource loading. This avoids requiring `offscreen` and keeps fetched pages outside privileged DOM contexts.

A unique selector is mandatory for selected-element and price monitoring. Missing or multiple matches fail; selectors do not silently recover to another element. Whole-page extraction removes active/non-readable elements, preserves paragraph boundaries, then applies only configured noise controls. ISO-date suppression is explicit; dates/numbers remain by default. Ignored phrases are literal text, not executable regexes.

Every new normalized text hash creates a version, including non-alerting rule changes. A first success establishes a baseline without an alert. On subsequent successes the baseline advances, the applicable rule evaluates the previous/current values, and unread increases only for alerting events. Hash-identical checks do not create versions. Errors never advance baselines. Reset baseline keeps archival history but clears active price/baseline state; the next success starts afresh. Clearing history keeps the current baseline. Mark as read clears the monitor's unread count.

Word/paragraph diffs have 120ms computation budgets. On timeout, they conservatively show the full previous text as removed and full new text as added, preserving both source texts. Policy rules use keywords in changed paragraphs; reordered paragraphs may appear as removal/addition. The price parser requires one numeric candidate and one explicit currency. `$` and `¥` are preserved as ambiguous currency symbols, never guessed as a particular national currency. Currency-token changes require explicit baseline reset.

Native notification requests occur after data commits. First consecutive failures can notify once; subsequent failures use backoff and health UI. Notification clicks open the relevant history. OS presentation is beyond the extension's control. There are no email/SMS or cloud endpoints.

IndexedDB version 2 separates lightweight `monitors` metadata from `texts` containing baseline, threshold reference and initial preview. `snapshots` contains full history; `snapshotMetadata` has a per-monitor index and stored UTF-8 record sizes. `accounting` holds the running logical byte total and record counts, including the original JSON-array punctuation semantics. A check reads only its own history metadata; baseline, snapshot, pruning metadata and byte ledger commit in one transaction. Metadata-only scheduler/badge/dashboard reads do not load `texts` or full snapshots. Full scans are reserved for explicit export. Preference retention changes prune history through metadata without reading baseline text.

The version 1 upgrade scans the old stores once inside the version-change transaction, preserving all monitors and snapshots and recovering missing threshold references from retained alert/initial snapshots. Invalid records abort the upgrade and leave version 1 data intact. Profiles already over budget, including from adding missing references, retain their data and must free space before a successful check can commit. Metadata health/error writes retain the earlier behavior of remaining possible at the logical budget boundary, with their sizes still accounted. Retention defaults to 40 versions, configurable from 10 to 200. The 50 MiB logical budget excludes physical IDB/index overhead; no fixed total monitor-count cap remains. New configurations enforce the byte budget; existing failure metadata remains writable. Export/import format version remains 1 and full export includes the reconstructed texts and company profiles; optional authenticated encryption wraps backup files.

Theme roles are centralized in CSS. System uses `prefers-color-scheme`; Chrome does not expose custom theme accents to this extension. Roboto and original SVG/PNG branding ship locally. Product identity is centralized in the model; the manifest, documentation, export filename, and database name remain straightforward migration points for a future rename.
